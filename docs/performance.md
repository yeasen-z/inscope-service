# 实测性能：历史环境快照与测量边界

本文保留在 **301-A06（8×H200）** 上对 `inscope-service` 的真实引擎及本机服务测量记录，不是模拟数据，**也不是当前 0.6.0 的重新测量**。记录来自不同实验，不能拼成一次调用的加法拆解。

当前实现每次真实 `/generate` 前增加 `/model_info` 身份核验，并共享请求额度、限制后端 HTTP 在途数、收紧校验和 deadline；下列快照未覆盖这些成本。未进行新测量，不应将旧数字作为当前延迟或容量承诺。

## 历史环境

| 项 | 值 |
| --- | --- |
| 机器 | 301-A06，8×H200 |
| 引擎 | sglang-inscope `8a2998b`，Qwen3-8B-FP8，单卡（GPU 6） |
| 引擎参数 | `--mem-fraction-static 0.75 --chunked-prefill-size 32768 --cuda-graph-bs-prefill 8192 16384 32768` |
| 探针 | `best_layers_08_16_24.pt`，层 9/17/25，位置 -4..-1，threshold 0.9 |
| profile 位置口径 | `position_mode=last`（`/info` 另报 `selected_positions=[-4,-3,-2,-1]`） |
| profile | `a6_nemotron_risk_faced_v1` |
| 网络 | 同机回环（服务与引擎均在本机） |

## 独立微实验：不能与 SDK 总延迟相加

历史记录给出了以下观测，但并非同一请求的互斥分段：

| 独立观测 | 历史值 | 可支持的结论 |
| --- | --- | --- |
| tokenize + chat template | 0.14 ms | 该样本的编排观测值，不代表所有长度 |
| 引擎 `/generate` 往返 | 约 88 ms | 某次引擎实验的往返值，不是确定的固定开销 |
| 特征采集对照的增量 | 约 24 ms | 独立采集实验的差值，不可加到另一实验的服务总耗时 |

另一组只生成、不采集的输入长度对照：

| 输入 | 历史只生成耗时 |
| --- | --- |
| 16 token | 92.88 ms |
| 200 token | 91.47 ms |

这两个样本耗时接近，但样本不足以区分调度、网络、缓存和前向计算各自贡献，不能证明耗时与长度无关、存在 88 ms 固定调度下限或“只能修改引擎调度才能降低”。旧文把 88 ms + 24 ms 与下节约 77 ms 总耗时放在同一加法表中是不成立的，此处拆开保留原始观测。

## 历史业务接口测量

### `/detect`

| 场景 | median | min | max |
| --- | --- | --- | --- |
| 短（约 30 token） | 77.4 ms | 76.6 ms | 78.0 ms |
| 批量 4 条 | 239.2 ms 总计 | — | — |
| 批量 4 条（简单均摊） | 59.8 ms | — | — |

简单均摊不等于单条请求延迟，也不证明 GPU 同次 batch、同次 forward 或吞吐提升的原因。HTTP 二维 input_ids 一次提交、返回多条独立记录只证明该协议跑通；需要引擎侧追踪和受控对照才能验证实际调度。

### `/audit`：串行检查点

| 场景 | 历史 median | 检查点数 |
| --- | --- | --- |
| 3 个工具返回 | 434.9 ms | 4 |
| 6 个工具返回 | 715.4 ms | 7 |

这两条轨迹的观测差约 93 ms/新增检查点，不是对任意轨迹的线性成本保证。另一次前缀缓存观测如下：

| 窗口 | 总 token | cached | 未命中 token |
| --- | --- | --- | --- |
| 1 | 33 | 0 | 33 |
| 2 | 53 | 33 | 20 |
| 3 | 73 | 53 | 20 |
| 4 | 93 | 73 | 20 |

这是特定输入与缓存状态的记录，不能推广为每步只算新增 token 或累计算力等同一次全长 forward。audit 截取消息前缀后仍由 profile 编排；A6 保留全部历史与 CoT，但模板末尾、探针位置和缓存驻留仍会影响实际复用。A5 的选窗规则不同。

## 当前模式与资源规则（不是性能测量）

- auto 在不超过 8 个单元时走 exact（单单元也可运行），超过时走 hierarchical；exact 全枚举需要 2^n 个组合。
- 层级默认每层组数上限 6；8 组可能一次用尽默认 256 预算。实际细化深度取决于去重、所选区域和剩余预算，不能由预算直接保证“可展开 4 层”。
- 根组超预算报错；细化预算不足保留粗区间并标记限制。数值并列不强行得出唯一分离结论。
- 评分层长度桶与后端位置组串行发送。detect 默认每桶 16 条，整批上限 128 条；analyze 默认每桶 8 条。
- detect/audit/analyze/ready 共享外部请求额度（默认 16），真实后端 HTTP 在途上限另为默认 16。它们不代表 GPU batch 大小。
- body 读取包含在请求 deadline 内；每次真实 generate 前核验 model_info，仍有检查与采集之间的竞态，不承诺原子性。

具体契约见 [多接口支持](<api-support.md>)，配置见 [README](<../README.md#配置参考>)。

## 引用与复测限制

1. **历史单请求、无并发负载**：没有容量、排队延迟、公平性或并发吞吐数据，不能推断并发必然降低均摊成本。
2. **同机回环**：跨机网络成本未覆盖。
3. **配置敏感**：显存、CUDA graph、采集位置、输入长度、缓存冷热都可能影响结果。不同时间、不同系统状态的数据不构成受控实验。
4. **没有当前校验成本数据**：增加身份核验、严格结果检查、body/deadline 和资源限制后需重测，本文不伪造新数值。
5. **`model_requests` 为 null**：算法评分器没有返回该计数；`cost.score_batches` 是算法评分轮数，不是 HTTP 或 GPU 请求次数。
6. **样本量小**：历史每组 3–20 次，以中位数为主，没有严格置信区间；原始逐次数据和完整采样条件不足以重建所有对照。
7. **验收范围有限**：延迟观测不等于 GPU 特征与训练缓存数值一致，也不等于检出率、误报率或生产就绪。

复测时应固定提交、模型、profile、请求数据、并发与缓存条件，分别记录端到端、model_info、generate、编排与打分耗时，并单独报告冷启动与暖态分布；不要将不同实验的统计量相加。部署步骤见 [快速开始](<../README.md#快速开始>)；本轮未启动或重启任何服务。
